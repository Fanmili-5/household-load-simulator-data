# 家庭模拟器的基础数据怎样组织

2026-09-08，字段设计草案。这里的 baseline 指以真实家庭为基础的训练数据表示，不是需求响应中的无事件基线用电量。本文提供文献依据和两户的映射示例，尚未替换仓库的全量 v2 数据，也不是新的训练数据发布。

## 先定义家庭，再映射问卷

我们希望模型根据家庭成员、住房、设备、使用习惯、历史用电和事件条件，预测这户家庭接下来一天的整户负荷。为此，SGSC 和 iFlex 应使用同一套字段定义。原始问卷只负责提供这些字段的取值。

现在已经做了信息提取和部分归一化，但还没有完成这个框架：`appliances` 的条目有的只有数量，有的只有有无，有的混入供暖用途；`household` 中还留有问卷字段名；习惯与设备、供暖系统的对应关系也没有统一。问题不在于 yes/no 不能使用，而在于它只能回答一个具体问题，不能替代完整的设备表示。

这些论文支持我们组织哪些信息、如何区分信息的作用。下面的 JSON 字段名、缺失处理及 SGSC/iFlex 映射是本项目的设计，并非论文给出的现成 SFT 格式。论文也不保证采用这些字段后 SFT 一定优于其他方法。

## 建议采用的字段框架

| 模块 | 回答什么问题 | 主要内容 |
| --- | --- | --- |
| `household` | 谁住在这里？ | 人数、家庭结构、年龄分布、就业/退休情况、教育与收入区间；保留“受访者”与“全户”的区别。 |
| `dwelling` | 住在什么环境？ | 住房类型、面积区间、建造年代、所有权、改造情况、供暖房间数。 |
| `appliances` | 有哪些设备，各有多少？ | 统一设备类别、存在状态、数量、子类型；功率和容量仅在有真实记录时填入。 |
| `energy_services` | 如何满足供暖、热水等需求？ | 供暖、制冷、热水、烹饪的能源和技术；在能够确认时关联设备类别，记录主要/辅助用途。 |
| `usage_habits` | 人和设备平时如何活动？ | 工作日白天在家、设备使用频率、时间段、供暖控制方式、夜间/外出调温。每条记录指定适用对象。 |
| `preferences` | 住户明确表达了什么偏好？ | 舒适温度、节电努力、是否关注电价和用电等实际回答；不推导“价格敏感型”等人格。 |
| `history` | 此前实际如何用电？ | 同户、预测时点以前的连续负荷序列，保留起止时间、采样间隔和单位。 |
| `context` | 这次预测处于什么条件？ | 预测窗口、事件时间、奖励/价格含义、地点；天气只使用已关联且当时可获得的数据。 |
| `output` | 模型应预测什么？ | 目标窗口的整户用电序列。设备级轨迹或 accept/reject 不作为现有实测标签。 |

车辆中的电动车进入设备清单；全户汽车总数留在家庭交通信息中。光伏、储能、通风和燃气服务也需要进入对应设备或系统模块。联系授权、试验分组、问卷原文、源字段名放入 `metadata/provenance`；电表构成和负荷计量口径仍须保留，防止把不同口径的总量视为相同物理量。

### 设备列表怎样写

`appliances` 按设备类别记录，不凭空创建具体设备实例。每项使用相同的键：

```json
{
  "type": "air_conditioner",
  "present": true,
  "count": null,
  "subtype": "split_system",
  "rated_power_w": null
}
```

这表示“确定有分体空调，台数和额定功率未记录”。它比 `HAS_AIRCON=Y` 多表达了类别和子类型，也明确了数量不能被猜成 1。`count` 是实物设备数量；不能拿供暖房间数、设备拥有率或供暖方式个数替代。

建议用统一设备类别目录支持两份数据：制冷/采暖、热水、冷藏、洗涤/烘干、烹饪、照明/娱乐、泳池泵、电动车、光伏及储能等。目录覆盖一种设备不等于源数据调查了它。没有调查的类别填未知，并在来源记录中注明；不能把空列表或缺失记录解释为全户没有设备。目录中的上下位类别需要互斥计数规则，例如未确定地源供暖是否就是已记录热泵时，不相加。

### 习惯必须带着对象

设备的有无、用途和使用方式分别记录。例如 iFlex 的“热泵是主要热源”进入供暖服务；“按时间自动控制供暖”进入供暖系统的控制习惯；24°C 进入客厅舒适偏好。三个事实可以一起用于预测，但不能组合成“这台热泵每天固定在某时刻启动并保持 24°C”。

`usage_habits` 的条目建议统一为 `subject_type`、`subject_id`、`behavior`、`value`、`unit` 和 `time_scope`。对象可以是全户、某类设备或某项能源服务。问卷只问全户供暖时，不能擅自把回答绑定到每台设备。使用频率只有等级时保留等级，不能换成自行设定的每周次数。

## 两份真实记录怎样映射

下面只演示容易混淆的字段。机器可读的[SGSC 示例](../examples/framework_design/sgsc_profile_fragment.json)和[iFlex 示例](../examples/framework_design/iflex_profile_fragment.json)是字段映射片段，包含同样的设备条目结构和逐条来源，不是完整画像或可直接训练的样本。

| 记录 | 已有真实信息 | 放入框架后的含义 |
| --- | --- | --- |
| SGSC 10041674 | 冰箱数量 1 | `appliances`：冰箱，存在，数量 1。 |
| 同上 | 有空调，类型 SplitSystem | `appliances`：分体空调，存在，数量未知。 |
| 同上 | 烘干机使用 NONE | `usage_habits`：报告不使用；设备是否拥有、数量仍未知。 |
| 同上 | 泳池泵 N | `appliances`：不存在；数量 0 为由明确不存在转换得到的逻辑值，注明转换规则。 |
| 同上 | 使用燃气供暖、热水、烹饪 | `energy_services`：分别保留三项服务；不能凭此创造三台具体燃气设备。 |
| iFlex Exp_1 | 2 人，2 人为 67 岁以上，2 人退休 | `household`：保留家庭人数、年龄和退休人数；不合成为虚构个人档案。 |
| 同上 | 热泵是主要热源 | 设备存在，数量未知；供暖服务中的角色为主要热源。 |
| 同上 | 自有电热水器 | 电热水器存在，数量未知；关联热水服务。 |
| 同上 | 按时间自动控制供暖 | 供暖系统有定时控制，具体时刻未知。 |
| 同上 | 客厅舒适温度 24°C | 偏好值；不是实测室温、温控器实际设定值或允许调整范围。 |

两份数据都使用这套定义，但有值的字段可以不同。iFlex 未提供完整白色家电清单，SGSC 当前家庭资料缺少人数等人口信息；统一格式并不能消除这些覆盖缺口。

## 如何接到后续 SFT

拟采用的任务仍是“家庭资料 + 过去 7 天负荷 + 当天条件 → 接下来 24 小时整户负荷”。这是项目选择，不是上述论文唯一规定的窗口。输出单位为各时间间隔的 kWh，SGSC 的 30 分钟和 iFlex 的 60 分钟间隔用同一个字段声明；如后续需要统一间隔，再明确重采样规则。

当前仓库只有两个独立的全天例子已按该窗口构造，全量旧样本尚未全部迁移，不能称为已完成统一 SFT。实施时需依次完成：完整设备目录及语义字典、两份数据的逐字段映射、全量重建、同户与时间边界核对。原始答案只作为追溯材料，模型输入使用整理后的语义字段。不得用目标当天负荷反推输入习惯，也不得把别户的资料补到该户。

这一设计为后续 SFT 提供结构明确、可追溯的条件信息。能否准确预测多设备家庭的负荷、缺失设备信息造成多大影响，仍需在后续实验中判断。
