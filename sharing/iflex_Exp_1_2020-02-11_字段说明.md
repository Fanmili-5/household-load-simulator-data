# iFlex 完整 JSONL 样本说明

对应文件：`iflex_Exp_1_2020-02-11.jsonl`。

这是 benchmark v1.0.0 中家庭 Exp_1 在 2020-02-11 的完整一条记录，版本为 `household-benchmark/1.0.0`。文件没有删字段、截断数组或加入省略号，与发布数据中的对应样本解析后完全相同。

JSONL 每一行是一个完整 JSON 对象。本文件只有一行，即一条家庭日样本。编辑器自动折行不表示文件里有多条样本。它是 benchmark 数据记录；尚未转换成 `system/user/assistant` 消息。

## 1. 整条记录的结构

| 字段 | 用途 |
|---|---|
| `schema_version` | 字段格式版本，固定为 `household-benchmark/1.0.0` |
| `sample_id` | `iflex:Exp_1:2020-02-11`，用于关联与评分，不进入模型输入 |
| `input.profile` | 这户的家庭、住房、设备、能源服务、习惯、偏好及逐车资料 |
| `input.history` | 同户目标日前连续七天的小时电量 |
| `input.context` | 目标窗口、地区、计量范围及当天实验价格 |
| `output.energy_kwh` | 同户目标日真实的 24 个小时电量，作为监督答案 |
| `metadata` | 来源、质量、输入时间证据和适用范围，不进入模型输入 |

这户有两位退休成员，均为 67 岁以上，住在 Bergen 的自有独立住宅。主要用热泵供暖，有独立电热水器，有一辆汽车，但没有电动车或插混汽车。模型输入还包括一般习惯、历史用电和当天实验价格。

## 2. 家庭资料 `input.profile`

### 2.1 家庭成员 `household`

| 字段 | 这条记录及解释 |
|---|---|
| `resident_count` | 2 人 |
| `composition` | `couple_without_children_living_at_home`：夫妻，无子女同住 |
| `respondent_sex` | `man`：受访者为男性，不能解读为家庭两人均为男性 |
| `highest_household_education` | `secondary`：家庭最高教育程度为中学 |
| `gross_income_band` | 收入区间未知；币种 NOK；统计周期 `period` 未确认 |
| `age_group_counts` | 各年龄段人数；`67_plus=2`，其余年龄段为 0 |
| `life_status_counts` | 各生活状态人数；`retired=2`，其余为 0。一般情况下生活状态可能重叠，不强制相加等于总人数 |
| `car_present`、`car_count` | 明确有汽车，数量为 1，表示全部汽车 |
| `internet_access` | 未知 |

年龄段键依次为 `0_1`、`2_5`、`6_15`、`16_22`、`23_29`、`30_39`、`40_49`、`50_66`、`67_plus`。生活状态键为在校或幼儿园、学生、兼职、全职、失业或未在读、退休、其他，对应文件中的英文键。

区间对象的 `lower`、`upper` 表示下界和上界；`lower_inclusive`、`upper_inclusive` 表示是否包含边界。`null` 边界可能表示未知或开放区间，需结合其他边界及来源解释。本条收入两端均未知。

### 2.2 住房 `dwelling`

| 字段 | 这条记录及解释 |
|---|---|
| `type` | `detached_house`：独立住宅 |
| `owner_occupied` | `true`：自有住房 |
| `energy_renovation_reported` | `false`：未报告做过题目所指节能改造 |
| `rental_unit_present` | `false`：没有出租单元 |
| `rental_unit_separate_meter` | `null`：出租单元分表问题未提供可用回答；不凭此推断其他计量状态 |
| `shared_flat` | 未知 |
| `heated_room_count` | 供暖房间数未知，不是供暖设备台数 |
| `floor_area_m2` | 80–99 m²，保留区间，不用中点代替 |
| `construction_year` | 1946–1960 年，保留区间 |
| `source_classified_type` | 来源分类的房型，区别于上面的问卷房型；本户未知 |
| `climate_zone` | 气候分区未知 |

### 2.3 设备清单 `appliances`

文件固定列出 20 类设备。每条设备项采用同一结构：

| 字段 | 含义 |
|---|---|
| `type` | 设备类别 |
| `present` | 是否持有：`true` 为有、`false` 为明确无、`null` 为未知 |
| `count` | 数量；有设备但没有记录台数时仍为 `null` |
| `subtype` | 子类型，没记录时为 `null` |
| `rated_power_w` | 额定功率 W，未知不估计 |
| `capacity_kw` | 适用设备的功率容量 kW，例如光伏容量；区别于额定功率字段 |
| `capacity_kwh` | 适用设备的能量容量 kWh，例如储能容量 |

本户的已知设备信息：

- `heat_pump`：有热泵，台数、额定功率等未知。
- `electric_water_heater`：有电热水器，`subtype=separate` 表示独立式；台数未知。
- `electric_or_plugin_hybrid_vehicle`：明确没有电动车或插混汽车，数量 0。这与有一辆汽车并不矛盾。
- `solar_pv`：明确没有光伏，数量 0。

其他 16 类设备的持有情况均未知，包括冰箱、冷柜、洗衣机、洗碗机、烘干机、空调、电暖器、电地暖、壁炉或柴炉、燃料供暖器、泳池泵、储能、机械通风、电炊具、电视和照明。未知不表示该户没有冰箱、电视或灯。

20 类目录不代表 20 类都调查过。空调与热泵等类别可能重叠，不能把所有设备数量相加称为家庭设备总数。

### 2.4 能源服务 `energy_services`

| 字段 | 含义与本户值 |
|---|---|
| `space_heating.gas_used` | 是否用燃气供暖，本户未知 |
| `space_heating.options` | 各种供暖技术的用途；热泵为 `main`，其他列出的方式为 `not_used` |
| `hot_water.gas_used` | 是否用燃气热水，本户未知 |
| `hot_water.technology` | `separate_electric_water_heater`：独立电热水器 |
| `cooking.gas_used`、`other_gas_use.gas_used` | 做饭及其他用途是否用燃气，本户未知 |
| `ventilation.technologies` | `natural_ventilation`：自然通风 |
| `supply` | 燃气接入、电力合同、账单接收、绿色电力、光伏配套电池及农场或经营活动共表等信息 |

供暖选项中的 `technology` 是技术类别，`device_type_ref` 指向关联设备类别，`role` 是用途（主要 `main`、辅助 `additional`、不使用 `not_used`）。“不使用电暖器供暖”不能推出“没有电暖器”。

本户 `supply.respondent_receives_bill=true`、`farm_or_business_shares_meter=false`；其余 supply 字段未知。`battery_connected_to_pv` 只描述光伏配套关系，不能据此推断全户储能持有情况。

### 2.5 使用习惯 `usage_habits`

每条习惯有六个字段：`subject_type` 是家庭/设备类别/能源服务，`subject_id` 指明对象，`behavior` 指明行为，`value` 是回答，`unit` 为适用单位，`time_scope` 是时间范围。

| 行为 | 本户回答 |
|---|---|
| `someone_home` | 工作日白天通常有人在家，`true` |
| `lower_temperature_in_less_used_rooms` | 会降低少用房间的温度，`true` |
| `reduce_temperature_at_night_or_away` | 夜间或外出时降低温度，回答为 `false` |
| 供暖 `control_mode` | `time_scheduled`，按时间自动控制 |
| 热水 `control_mode` | `none`，题目所问控制措施回答为没有；不能据此断言热水器没有恒温器 |
| 烘干机 `reported_use_level` | 未知 |
| 柴炉 `reported_use_conditions` | 未知 |

`weekday_daytime` 是工作日白天；`usual` 表示一般习惯，不是目标日的实测操作或具体开启时刻。本户习惯的 `unit` 都为 `null`，因为是布尔或类别回答。

### 2.6 偏好 `preferences` 与车辆详情 `vehicle_details`

`living_room_comfort_temperature_c=24` 表示自报客厅舒适温度 24 ℃，不是当天室温，也不是设备允许调整范围。

`follows_electricity_use=false`、`follows_electricity_prices=false` 表示回答不关注用电量和价格；`reported_electricity_reduction_effort`、`use_information_channels`、`price_information_channels` 未知。

`vehicle_details=[]` 表示本户没有电动车或插混汽车可供展开，不代表没有普通汽车。有电动车的其他家庭会在这里记录同户的充电地点、频率等来源信息。

## 3. 历史用电 `input.history`

- `start`：2020-02-04 00:00。
- `end`：2020-02-11 00:00，结束时间不包含在历史窗口内。
- `interval_minutes=60`，`unit=kWh`。
- `energy_kwh` 完整保存 168 个值，没有省略。第 i 个值（从 0 编号）对应 `[start+i小时, start+(i+1)小时)`。

例如第一个值 2.870 是 2 月 4 日 00:00–01:00 的电量，最后一个值 2.348 是 2 月 10 日 23:00–24:00 的电量。无需逐点重复时间字符串，起点、间隔和数组位置已经共同确定全部时间。

## 4. 目标日条件 `input.context`

`forecast_origin` 为 2020-02-11 00:00；`target_window` 从该时刻到 2020-02-12 00:00，`horizon_hours=24`，间隔 60 分钟。

`country=NO`、`region=Bergen`。`time_basis=source_clock_intervals_no_utc_conversion` 表示使用来源时钟，没有自行假设 UTC 偏移。

`measurement_scope` 表示使用来源记录的家庭需求，筛选时没有报告光伏、农场或经营共表、出租单元共表。不能把它解读为实测逐电器负荷。

`events` 里有一项全天实验价格条件：`type=experimental_price_for_reward_calculation`。`currency=NOK`，`price_per_kwh` 有 24 个值，`price_interval_minutes=60`。这是实验奖励计算信号，不是零售电费。`rate_per_reduced_kwh=null` 是另一个奖励费率字段未提供适用值，不能当成零。

## 6. 追溯信息 `metadata`

| 字段 | 解释 |
|---|---|
| `source`、`profile_id`、`source_sample_ids` | 来源与同户关联 ID |

| `condition_evidence_groups` | 活动条件的证据分组 |
| `construction_status` | 表示已核查观测日构造，不代表所有输入时间都已核实 |
| `availability.history_precedes_origin` | 历史窗口在预测起点前，本条为 true |
| `profile_individual_time_verified`、`event_notice_individual_time_verified` | 逐户问卷时刻及通知送达时刻未核实，本条均为 false |
| `profile_protocol` | 原文说明 Survey 1 在参加试验前完成 |
| `event_notice_protocol` | 第一阶段协议为前一天 15:00 发送；`event_notice_protocol_is_receipt_evidence=false`，不是个体送达证据 |

| `quality.daily_totals_kwh` | 七天历史和一天目标的每日合计，共 8 个值；包含目标日信息，不能进入模型输入 |

| `eligibility.retrospective_conditional` | 可以进入回顾性条件预测集合，本条 true |

## 7. 后续如何用于 SFT

当前文件保留原 benchmark 结构。导出 SFT 时：

1. system 消息说明预测范围、单位及输出格式。
2. user 消息放 `input` 的对应输入版本。
3. assistant 消息放 `output`，训练时作为答案；实际预测时不提供。
4. `sample_id` 与 `metadata` 留在追溯区，尤其不能把含目标日合计的质量信息送入输入。

训练损失应限制在答案内容；具体 tokenizer、上下文长度和损失掩码在模型接入时核查。本次只是导出与说明，没有训练模型。

读取完整 JSONL：

```python
import json
from pathlib import Path

path = Path("iflex_Exp_1_2020-02-11.jsonl")
with path.open(encoding="utf-8") as f:
    sample = json.loads(next(f))

print(sample["sample_id"])
print(len(sample["input"]["history"]["energy_kwh"]))  # 168
print(len(sample["output"]["energy_kwh"]))           # 24
```
